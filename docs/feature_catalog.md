# ReconLens — Feature Catalog

Generated features for the reconciliation match classifier (Phase 3+). Every
feature here must be defensible in an interview — that's the bar this catalog
is written to.

## Numeric

**abs_amount_diff**
Source: `ledger.amount`, `settlement.amount`
Transformation: `|ledger_amount - settlement_amount|`
Type: float, non-negative
Expected range: `[0, ~12000]` observed; unbounded in principle
Missing-value behavior: n/a (amounts are always present in this dataset)
Why it matters: the single strongest raw signal for "same transaction" — but not sufficient alone, since a large ledger amount can have a small absolute diff purely by chance.

**relative_amount_diff**
Source: derived from `abs_amount_diff` / `ledger.amount`
Transformation: normalized by ledger amount (ledger treated as source of truth)
Type: float, non-negative
Expected range: `[0, ~0.05]` observed (bounded by generator's fee/drift model)
Missing-value behavior: raises `ValueError` if ledger amount ≤ 0 (data-quality failure, not a feature case)
Why it matters: makes ₹1.50 off on a ₹50 transaction and ₹1.50 off on a ₹5,00,000 transaction comparable, which `abs_amount_diff` alone cannot do.

**amount_ratio**
Source: `settlement.amount / ledger.amount`
Type: float
Expected range: `[0.95, 1.05]` observed
Why it matters: directional signal (fee deductions push this below 1.0) that `relative_amount_diff` collapses by taking an absolute value.

**date_diff_days**
Source: `ledger.txn_date`, `settlement.txn_date`, both parsed via `pandas.to_datetime` before subtraction
Type: int, non-negative in this dataset (settlement never precedes the transaction)
Expected range: `[0, 7]` (candidate generation's date window)
Why it matters: settlement lag is a real, bounded phenomenon; large date gaps are evidence against a match.

## String similarity (computed on normalized vendor names — see Normalization below)

**vendor_levenshtein_similarity**, **vendor_jaro_winkler_similarity**,
**vendor_token_sort_similarity**, **vendor_token_set_similarity**
Source: RapidFuzz, applied to `normalize_vendor()` output on both sides
Type: float in `[0, 1]`, 1.0 = identical
Why four metrics instead of one: they fail differently. Levenshtein penalizes any character-level edit; token-sort/token-set tolerate word reordering and subset relationships; Jaro-Winkler over-weights shared prefixes. **Known limitation, observed directly in this dataset:** Jaro-Winkler can score two genuinely unrelated vendor names above 0.6 purely from shared short substrings — this is a real property of the metric, not a bug, and it's exactly why the classifier gets four independent string signals plus amount/date/reference/embedding evidence rather than relying on any one of them.

**vendor_exact_normalized_match**
Type: binary. Input feature only — never the reconciliation decision itself (see `string_similarity.py` docstring).

## Semantic

**vendor_embedding_cosine_similarity**, **description_embedding_cosine_similarity**
Source: local `sentence-transformers/all-MiniLM-L6-v2`, cosine similarity between embeddings
Type: float in `[-1, 1]`
**Important caveat, current build environment:** this dev sandbox has no network route to huggingface.co, so these numbers were generated by a documented deterministic character n-gram hashing fallback (`backend=fallback_ngram_hash` in every metadata/report file), not the real semantic model. The fallback is lexical-overlap-only — it will not recognize "TCS" as related to "Tata Consultancy Services" the way a real embedding model would. This is flagged automatically in `reports/feature_quality_report.md` whenever it's active, so results are never mistaken for genuine semantic similarity. Fix planned for Phase 8: pre-bake model weights into the Docker image so this never depends on runtime network access.

## Reference-ID

**reference_exact_match**, **reference_substring_overlap**, **reference_similarity**,
**reference_missing_ledger**, **reference_missing_settlement**, **reference_both_missing**
Source: `normalize_reference()` on both sides (uppercase, strip whitespace/separators)
Type: binary / float `[0,1]`
Missing-value behavior: **the one rule this whole module exists to enforce** — `is_missing_reference()` is checked before any comparison, so two missing references can never register as `reference_exact_match=1`. Verified by `test_reference_missing_never_counts_as_exact_match`.
Why `reference_similarity` exists alongside `reference_substring_overlap`: overlap is binary (contains or doesn't); similarity uses longest-common-substring length so partial corruption in the middle of a reference still registers as partial evidence.

## Structural

**candidate_count_for_ledger**, **candidate_count_for_settlement**, **competing_candidate_count**,
**is_potential_one_to_many**, **is_potential_many_to_one**
Source: shape of the candidate set after blocking (`ml/features/structural.py`)
Type: int / binary
Why these and not the true structural label: the true one-to-one/split/batched label is hidden ground truth and must never reach a feature. These features instead describe what the model can actually observe — how many alternatives a given pair is competing against — which is legitimate signal a human reconciler would also use ("this settlement line has 3 plausible ledger matches, so I should look more closely before trusting a high raw amount-similarity score").

## Known dataset-level limitation (candidate generation, not feature engineering)

Candidate-generation recall against hidden ground truth: **80.3%** (502/625 true pairs recovered). The entire 19.7% gap is split/batched-settlement components whose amounts fall outside a single-record blocking window by construction — confirmed by direct breakdown (0 one-to-one losses, 123 split/batch losses). This is a documented scope boundary for Phase 2's blocking approach, not a silent gap; recovering it would need a combinatorial-sum blocking pass, deferred to a later phase if time allows.
